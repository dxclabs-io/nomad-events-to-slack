# Commitizen

This repo uses [Commitizen](https://commitizen-tools.github.io/commitizen/) to bump the
project version, tag the release, and generate the changelog from Conventional Commits -
automatically, on every merge to `master`. There's no manual release step.

## What actually happens

`.github/workflows/bump.yaml` runs on every push to `master` (skipped if the triggering
commit already starts with `bump:`, to avoid bumping the bump commit):

1. Installs `commitizen` and runs `cz bump --yes --changelog`.
2. Commitizen looks at every commit since the last version tag, works out the highest bump
   level implied by their messages (see below), updates the version, writes a changelog
   entry, and creates a new commit + tag.
3. The workflow pushes that commit and tag back to `master`.
4. The new `v*` tag triggers `.github/workflows/deploy.yaml`, which deploys the release to
   production on Nomad.

Because this repo squash-merges PRs, **the PR title becomes the single commit message**
commitizen sees for the whole PR - so the PR title has to itself be a valid Conventional
Commit (`feat: ...`, `fix: ...`, etc.). A non-conventional title means commitizen doesn't
recognise any commit worth bumping for, and the workflow silently no-ops (no version bump,
no tag, no error).

## Bump level mapping

Configured under `[tool.commitizen.customize]` in `pyproject.toml`:

| Commit prefix | Bump |
|---|---|
| `feat` | MINOR |
| `fix`, `perf`, `refactor`, `build` | PATCH |
| any type with a trailing `!` (`feat!:`), or a `BREAKING CHANGE` footer | MAJOR |
| `chore`, `ci`, `docs`, `style`, `test`, `revert`, `bump` | no bump |

A bump means a production deploy, so pick the prefix accordingly: changes that shouldn't
ship a release (docs, CI tweaks, local tooling) belong under a no-bump prefix.

## Version source of truth

`version_provider = "pep621"` - `[project].version` in `pyproject.toml` is authoritative, and
it's the only place the version lives (there are no `version_files`).

## Tag formats

`tag_format = "v$version"` (e.g. `v0.8.3`). Every tag in this repo already uses that
format, so no `legacy_tag_formats` / `ignored_tag_formats` settings are needed.

## Changelog

`changelog_file = "docs/changelog.rst"`, `update_changelog_on_bump = true` - every bump
prepends a new dated section built from the same commit messages used to decide the bump
level. Don't hand-edit this file; it's regenerated by commitizen each time.

## Known quirk: uv.lock phantom diff

`cz bump` writes the new version into `pyproject.toml` but does **not** update `uv.lock`. The
next time anything runs uv against this repo, uv rewrites `uv.lock`'s self-referential
`nomad-events-to-slack` version line - an unrelated one-line `uv.lock` diff in `git status`.
CI's `uv-lock` hook does the same, so lint fails on every PR after a release until `uv.lock`
is synced.

## Checking locally

```powershell
uv run cz bump --dry-run --changelog   # see what the next bump/changelog entry would look like, without writing anything
```
